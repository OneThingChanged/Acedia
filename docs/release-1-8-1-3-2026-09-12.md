# Acedia 1.8.1.3 secondary account browser MCP hotfix

## Problem and result

Each registered Codex account uses a separate `CODEX_HOME`. The launch command
enabled `mcp_servers.multiagent_browser`, but a secondary account home could
lack the server's `command`, `args`, and `env_vars`. Codex therefore rejected
the incomplete enabled entry with `invalid transport` before starting the
session.

Before every local Codex launch, Acedia now merges the complete managed browser
MCP transport into the selected account's `config.toml`. The entry remains
disabled at rest and is enabled only for the Acedia-launched process. Existing
credentials and unrelated account settings remain intact, and the account home
does not receive the project's notification hooks.

The two registered secondary account homes present during diagnosis were
repaired immediately. Each original configuration was copied to
`config.toml.before-browser-mcp-1.8.1.3` in the same folder before the managed
transport was added. Direct Codex CLI inspection confirmed a valid enabled
stdio transport in both homes.
